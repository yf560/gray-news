# GRAY A 서버 분석 설계

## 의도

로컬 GRAY 데모에서 입력 기사 하나를 요약하고, 공개 웹 자료에 근거한 쟁점별 관점을 출처와 함께 반환한다. 사용자가 판단할 자료를 정리하는 기능이며 사실 판정은 하지 않는다.

## 목표와 범위

- `POST /api/analyze`가 URL 또는 본문을 받고 버전이 있는 구조화 JSON을 반환한다.
- 웹 검색 단계와 구조화 단계의 두 번의 OpenAI Responses API 호출로 역할을 분리한다.
- 각 관점에 서버가 발급한 출처 ID가 연결된다.
- URL 원문을 확인하지 못하면 사용자가 본문을 붙여넣도록 안내한다.
- 입력 검증, API 오류, 타임아웃에 안정된 JSON 오류 코드를 반환한다.
- 표준 라이브러리와 기존 테스트용 `opener` 주입 방식을 유지한다.

## 제외 범위

프론트엔드, 로그인, 사용자별 서버 기록, 자동 이슈 추적, Tavily, 별도 RAG 저장소, 배포는 다루지 않는다.

## 접근 방식

1. 단일 검색 프롬프트에서 모든 카드를 한 번에 생성하면 구조와 인용이 섞여서 출처 검증이 어렵다.
2. 검색 후 출처를 추출하고, 검색 결과만 넣은 두 번째 호출에서 JSON Schema를 강제한다. 기존 단일 서버와 API 통합을 재사용하면서 근거 목록과 화면 계약을 분리할 수 있어 이 방식을 채택한다.
3. 자체 수집기와 검색 인덱스를 구축하면 통제력은 높지만 6주 로컬 데모 범위를 넘는다.

## API 계약

요청은 `POST /api/analyze`, `Content-Type: application/json`이며 `{ "url": "https://...", "text": "..." }`를 받는다. 둘 다 있으면 본문이 우선한다. 기존 `{ "article": "..." }` 요청은 호환한다.

성공 응답은 아래 형태다.

```json
{
  "version": 1,
  "title": "기사 제목",
  "summary": "핵심 요약",
  "issues": [{
    "question": "쟁점 질문",
    "perspectives": [{
      "actor": "입장 이름",
      "claim": "주장 요약",
      "evidence": "근거 요약",
      "sourceIds": ["S1"]
    }],
    "note": null
  }],
  "sources": [{"id": "S1", "title": "출처 제목", "url": "https://example.org/source"}]
}
```

검색 근거가 부족하면 모델은 관점을 지어내지 않고 쟁점의 `note`에 자료 부족을 쓴다. 서버는 존재하는 출처 ID만 허용하고, 유효 출처가 없는 관점은 제거한다. 쟁점이 없으면 `issues: []`를 반환한다.

오류 JSON은 `{ "code": "...", "error": "..." }`다. 입력 오류 `400 INVALID_INPUT`, 원문 확보 실패 `422 ARTICLE_UNAVAILABLE`, 분석 실패 `502 ANALYSIS_FAILED`, 시간 초과 `504 ANALYSIS_TIMEOUT`으로 구분한다.

## 안전과 한계

- URL은 검색 도구로 조회하며 서버가 임의의 사용자 URL로 직접 요청하지 않는다.
- 검색 자료에 포함된 지시는 따르지 않고 인용 가능한 참고자료로만 취급한다.
- URL 원문 확인은 검색 호출에서 입력 URL과 일치하는 HTTP(S) citation이 있는지를 기준으로 한다. 일치하지 않는 리다이렉트나 짧은 URL은 본문 입력으로 복구한다.
- 출처 연결은 모델이 해당 관점을 지지하는지 의미적으로 보증하지 않는다. 데모 중 실제 기사 3건에서 수동 확인한다.

## 검증 계획

모의 OpenAI 응답으로 검색과 구조화 두 호출을 확인한다. 원문 URL 누락, 잘못된/미등록 출처 ID, 빈 관점, 잘못된 JSON, 미완료 API 응답, 타임아웃, 입력 경계값, 레거시 요청 호환을 자동 테스트한다. 마지막으로 로컬에서 실제 기사 3건을 넣고 쟁점과 출처 연결을 사람이 점검한다.
